- 공통 원인: Tomcat이 서비스가 아니라 **콘솔 창이나 수동 명령에 묶여 있다.**
- 이번 재기동 방식: `catalina.bat run`을 **숨김 창**에서 실행했다. 닫을 창이 없으므로 재부팅, 로그오프, `shutdown.bat` 전까지 유지된다.
- 권장 (승인 필요, 시스템 설정 변경): Tomcat을 Windows 서비스(`service.bat install`)로 등록. 등록하면 재부팅 후에도 자동으로 올라온다.

## 2. admin 비밀번호

**현황 (DB 읽기, 해시 값은 기록하지 않음)**
- `admin`: 사용 중, 권한 AUTH0001
- 해시: BCrypt(`$2a$`, 60자)
- 로그인 실패 4회 (11/17)
- **마지막 로그인 없음**
- **`PW_CHANGE_DT` = NULL** → PC-B DB에서는 비밀번호를 한 번도 바꾼 적이 없다.
  - PC-A에서 바꾼 비밀번호(10/27)는 PC-B DB로 옮겨오지 않았다.
  - 따라서 PC-B의 admin은 **이관 당시의 초기 비밀번호**다.

**제품 동작 (코드 확인, main `4915759`)**
- 비밀번호 재설정 기능 없음: 이메일, 관리자 초기화 API, 시작 시 초기화 모두 없다.
- 로그인 실패 잠금 없음: `LOGIN_FAIL_CNT`만 늘어난다.
- `PW_CHANGE_DT`가 NULL이면 로그인은 되지만 `passwordChangeRequired=true`다.
  - 비밀번호를 변경하기 전까지는 관리자 API(Client 등록 포함)가 막힌다(403).
  - 웹 화면은 변경 화면으로 이동한다.

**복구 방법**
- **A. DB 변경 없음 (권장, 먼저 시도)**
  1. 사용자가 웹(`http://localhost:8081/juprovider/`)에서 **초기 비밀번호**로 로그인한다. PC-A에서 바꾼 값이 아니다.
  2. 강제 변경 화면에서 새 비밀번호를 정한다.
  - Claude는 입력을 보지 않는다.
- **B. DB 직접 수정 (승인 필요)**: 초기 비밀번호를 모를 때.
  - 스크립트 `tools/ai_admin_pw_reset.ps1`은 준비만 했다. PC-B에 배포하지 않았고 실행하지 않았다.
  - 동작
    - 사용자가 창에서 임시 비밀번호를 입력하면, PC-B에서 서버와 같은 BCrypt 라이브러리로 해시를 만든다.
    - 기존 해시와 상태는 로컬 백업 폴더의 `restore_admin.sql`로 저장한다 (git 제외).
    - `USER_PW_HASH`를 갱신하고 `LOGIN_FAIL_CNT=0`, `PW_CHANGE_DT=NULL`로 둔다.
    - 임시 비밀번호로 로그인을 시험한다.
    - 다음 로그인에서 변경이 강제된다.
  - 대상은 `admin` 한 행뿐이다. 스키마 변경과 새 계정 생성은 없다.
