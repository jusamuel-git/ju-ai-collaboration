## 1. Desktop 앱에 CollectionPlan·수집 연결

### 1-1. 현재 구조 (main `4915759`)

**Client** (`juprovider.client`, WinForms)
- 로그인 → `DesktopAuthService.SyncAsync` → `sync/devices` (Client Key)
- 받은 장치는 로컬 Access DB(`LOCAL_DEVICE`)에 저장
- IPC로 `DeviceSync`·`DeviceConnect` 전송

**Terminal** (`juprovider.terminal`, 런타임 프로세스)
- `DeviceRuntimeManager`가 **가상 장치만** 처리한다.
- SERIAL·NETWORK는 `NotSupportedException`
- 데이터는 `DataReceived`(문자열)로 Client에 보낸다.

**검증된 라이브러리** (C5d, COM3 PASS)
- `JuProviderApiClient`: protocols·data-tags·data-map
- `CollectionPlanBuilder`
- `DeviceSession`, `LinkSupervisor`, `SerialTransport`
- **앱에서는 아직 쓰지 않는다.**

### 1-2. 목표 흐름

```
Client (로그인·Client Key)                    Terminal (런타임)
 ├ sync/devices            ─ 기존
 ├ 장치별(PtlGrpCd 있는 것):
 │   sync/protocols/{grp}, data-tags, data-map ─┐
 │   → 로컬 캐시(revision)                     │ IPC DevicePlanSync {devCd, group, tags, dataMap, revision}
 │                                             └→ CollectionPlanBuilder.Build(server → builtin → default)
 ├ IPC DeviceConnect / DeviceAction(START|STOP) → LinkSupervisor + plan.CreateSession(transport)
 │                                                 초기화 루틴 자동 · 재연결 시 재실행
 └ ← IPC DeviceStatus(Session/Link 상태, InitRoutine 결과, 계획 경고)
   ← IPC DataValues [{datGrCd, datCd, datIdx, value, quality, ts}]  (data-map 기준 TAG)
```

**원칙**
- **수집은 Terminal에서**, **서버 통신·인증은 Client에서** 한다.
  - Terminal은 Client Key를 모른다.
  - 키는 `client.json`에만 있고, Client 프로세스만 읽는다.
- 우선순위는 C5d 그대로: **서버 → 내장(D4 대체) → 기본**
  - `Plan.Sources`·`Warnings`를 상태 메시지로 Client에 보여 준다.
- 오프라인
  - 마지막으로 받은 서버 응답을 캐시한다 (장치별 JSON + revision).
  - 서버에 연결되지 않으면 캐시로 계획을 만든다. 출처는 `server(cached)`로 표시한다.
  - 캐시가 없으면 내장 → 기본 순서.
- **POLLING 유형은 자동 반복 송신하지 않는다.**
  - 현재 세션도 요청이 있을 때만 송신한다.
  - 3절의 오분류 프로토콜이 주기 송신되는 사고를 막는다.

### 1-3. 구현 범위 (제안, 3단계)

| 단계 | 내용 | 주요 파일 | 검증 |
|---|---|---|---|
| **C6a** Terminal 런타임 | `SerialDeviceRuntime`: Plan + LinkSupervisor + Session.<br>IPC 메시지 `DevicePlanSync`·`DeviceAction`·`DataValues` 추가.<br>`DeviceRuntimeManager`에 SERIAL 분기 추가 | `lib.ipc/Messages/*`, `terminal/Runtime/*` | 단위 테스트: IPC 직렬화.<br>가상 GTEC(`BuiltInProfiles` 시뮬레이터 + VirtualTransport)로 Terminal 단독 E2E |

### 1-4. 정할 것

- **장치 포트(COM 번호)는 PC마다 다르다.**
  - 기본안: 서버 `DEV_CONFIG`(장치 등록 값)를 쓰고, 로컬 `config/ports.json`(DevCd → COM)이 있으면 그 값으로 덮는다.
  - PC-B SDEV_GTEC01의 `DEV_CONFIG` 값은 확인이 필요하다 (설명란에 COM6이라는 기록이 있었고, 실제 연결은 COM3).
- **값 저장·서버 업로드는 이번 범위 밖으로 제안한다** (C7).
  - C6에서는 표시와 로컬 로그만 한다.
- **로컬 캐시 위치**
  - 파일(`app\cache\plan_<devCd>.json`)을 권장한다. Access 스키마를 바꾸지 않아도 된다.
  - LOCAL 테이블로 할 수도 있다.

### 2-3. 충돌·위험

1. **Jenkinsfile 충돌 (필수 수정)**
   - 현재 `Stop Tomcat` = `shutdown.bat`(8005), `Start Tomcat` = `startup.bat`
   - 서비스로 바꾼 뒤에 일어나는 일
     - shutdown.bat이 서비스의 JVM을 끝낸다. 서비스는 비정상 중지로 기록되고, 복구 동작이 설정되어 있으면 배포 중에 다시 켜질 수 있다.
     - startup.bat이 서비스 밖에 **두 번째 Tomcat**을 띄운다. 11/15 08:50 사고와 같은 유형이다.
   - 제안: 서비스가 있으면 `Stop-Service`/`Start-Service Tomcat10`, 없으면 기존 bat을 쓰도록 **분기한다** (하위 호환).
   - 이 수정을 서비스 전환보다 먼저 main에 반영한다.
2. **비밀 값 전달**
   - 선택지
     - procrun `--Environment`나 `JvmOptions -DJU_...`: 레지스트리 `HKLM\SOFTWARE\...\Procrun 2.0\Tomcat10\Parameters`에 평문으로 저장된다 (Users 읽기 가능).
     - **설정 파일 + 제한 ACL을 권장한다.** 리허설로 검증한 방식이다.
   - 파일 위치 제안: `C:\MyData\MyTool\tomcat\juprovider-secret\juprovider-secret.properties` (conf 밖, 전용 폴더, 상속 끊음)
3. **⚠ 기존 보안 이슈 (발견, 조치 안 함)**
   - `tomcat\bin`과 `conf`에 **Authenticated Users 수정 권한**이 상속되어 있다.
   - 그래서 현재 `setenv.bat`(DB 비밀번호·JWT secret)을 **PC-B 로그인 사용자 누구나 읽고 바꿀 수 있다.**
   - 서비스 전환 때 함께 정리할 것을 권장한다: bin·conf ACL 제한, setenv.bat의 JU_* 제거.
4. **로그**: 서비스는 stdout/stderr를 `logs\tomcat10-stdout/stderr.*.log`로 남긴다. 지금은 콘솔에만 나와 Spring 오류가 사라진다. 서비스로 바꾸면 개선된다.
5. **습관 변경**: 전환 후에는 `startup.bat`·`shutdown.bat`·숨김 `catalina.bat run`을 쓰지 않는다. 서비스 관리자나 `sc`만 쓴다.

### 2-4. 전환 절차 (승인 후, 관리자 PowerShell)

1. 현재 숨김 실행 중인 Tomcat(PID 5080) 중지: `shutdown.bat` → 8081 닫힘 확인
2. 비밀 설정 파일 작성
   - 사용자가 값을 직접 입력한다.
   - ACL: SYSTEM·Administrators만
3. `service.bat install Tomcat10`
   - 이어서 `tomcat10.exe //US//Tomcat10` 실행:
     - `++JvmOptions "-Dspring.config.additional-location=file:/…/juprovider-secret.properties"`
     - `--JvmMx 1024`
     - `--Startup auto`
   - 장애 복구: `sc failure Tomcat10 reset= 86400 actions= restart/60000`
4. `Start-Service Tomcat10` → health 200, 로그인 401, Client Key 200·401 확인 (C5d connect의 K 항목)
5. Jenkins #4로 배포 경로 검증: 서비스 분기 Jenkinsfile 기준, 같은 커밋 재배포
6. 재부팅 시험: 자동 기동 후 health 200
7. setenv.bat의 JU_* 제거, bin·conf ACL 정리

### 2-5. 복구

- 서비스 기동 실패나 이상
  1. `Stop-Service Tomcat10`
  2. `service.bat remove Tomcat10`
  3. 기존 방식(setenv.bat + startup.bat)으로 복귀
- WAR·DB는 바뀌지 않으므로 되돌릴 필요가 없다.

## 3. GTEC 10개 프로토콜 보완안 (DB 데이터 변경 → 승인 필요)

- 근거
  - 관리자 화면의 프로토콜명
  - `PTL_VAL`(송신 값)
  - 내장 GTEC 설정(0000·0001·0002·0100·0300·0301·0400)과의 대응
- 명령 의미는 **이름과 값으로 추정**했다. **GTEC 매뉴얼로 확인이 필요하다.**
- 참고: 실측 수집 속도는 3채널 × 10Hz다 (5초에 50프레임). `S{12,0.100}`(100ms)이 장비 기본값일 가능성이 있다.

| 코드 | 이름 | 현재 | 용도 판단 | 보완안 |
|---|---|---|---|---|
| GTEC0101 | PhotoGate I 모드 | POLLING, 값 `S{11,0}`, 역할 없음 | 모드 설정 (0100 `S{11,1}` 아날로그 모드와 같은 계열) | 유형 TX_ONLY(PROT0001), 역할 CONTROL, 멱등 Y, 동작 없음 |
| GTEC0102 | PhotoGate II 모드 | POLLING, `S{11,2}` | 모드 설정 | 위와 같음 |
| GTEC0103 | 실험중지 | POLLING, `S{10,0}[CR][LF]` | **GTEC0301(`S{10,0}`, STOP)과 중복** (CRLF만 다름) | **사용안함**. 0301이 STOP 동작을 맡는다. CRLF가 필요한 장비 펌웨어면 0301 값에 반영한다 |
| GTEC0104 | 고속채널 선택 | POLLING, `S{11,1}[CR][LF]` | 값이 0100(아날로그 모드 `S{11,1}`)과 같다. 이름과 값이 맞지 않는다 | **매뉴얼 확인 전 사용안함**. 고속 채널 선택 명령 값 확인 후 재정의 |
| GTEC0105 | 고속 샘플속도 설정(10ms) | POLLING, `S{12,10}[CR][LF]` | 샘플 간격 설정 (`12`=간격, 단위 확인 필요: 10ms면 `0.010` 표기와 불일치) | TX_ONLY, CONTROL, 멱등 Y. 값은 매뉴얼 확인 후 |
| GTEC0200 | 저속 샘플간격 100ms | POLLING, `S{12,0.100}` | 샘플 간격 설정 | TX_ONLY, CONTROL, 멱등 Y. 초기화 루틴에 넣을지 결정 (명시 설정 시 재연결 후에도 같은 속도) |
| GTEC0201 | 고속 샘플간격 20ms | POLLING, `S{12,0.020}` | 샘플 간격 설정 | TX_ONLY, CONTROL, 멱등 Y |
| GTEC0003 | 고속실험시작 | POLLING, 값 없음, 패킷 없음 | 고속 모드용 START (0300 `S{10,1}`의 고속판으로 보임) | **값을 정의하기 전에는 사용안함**. 정의 후 TX_ONLY, CONTROL, 동작 START(고속 계획에서만) |
| GTEC0401 | 고속 아날로그 데이터 | POLLING, 값·패킷 없음 | 고속 모드 수신 스트림 | **사용안함** 또는 RX_STREAM(PROT0002) + DATA 역할 + 해석 규칙. 고속 프레임 형식 확인 후 |
| GTEC0402 | 디지털 데이터 | POLLING, 값·패킷 없음 | 디지털(PhotoGate) 수신 스트림 | 위와 같음 |

**추가 정리 대상**
- **GTEC0000**
  - 해석 규칙이 비JSON 레거시 문자열(`패킷길이|STX DLE|ETX|ETX DLE`)이다.
  - 응답 판정(`startsWith {OK`)만으로 충분하므로 해석 규칙을 비울 것을 권장한다.
  - 다만 서버 API가 COALESCE라 null로는 비울 수 없다. 빈 값으로 처리한다.
- **⚠ 유형 표시 오류 (공통코드 다국어)**
  - LANG0001 이름이 코드 의미와 어긋난다.
    - PROT0000(POLLING) → "기본 프로토콜"
    - PROT0001(TX) → "**폴링**"
    - PROT0002(RX) → "**제어**"
  - 그래서 관리자 화면에서 GTEC0300 시작·0301 중지가 "폴링"으로, 0400 데이터가 "제어"로 보인다.
  - 보완: LANG0001을 POLLING "폴링", TX "송신 전용", RX "수신 전용"으로 바꾼다 (`ju_lang_text` 3행, 데이터 변경).
- **적용 방식 제안**
