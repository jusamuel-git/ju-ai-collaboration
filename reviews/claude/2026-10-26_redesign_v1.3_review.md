## 요약

- **단계 분리는 가능하다.** 다만 한 파일에 두 단계가 섞인 곳이 10곳이다 (2장). 파일 단위로 나눌 수 없어서, 단계별로 파일 내용을 다시 만들어 적용해야 한다.
- **설계를 고쳐야 할 점이 3가지 있다.**
  1. **JU-1A만 push하면 Vue 장치 화면과 Desktop 동기화가 깨진다.** JU-1A가 API를 잠그는데, 로그인 화면(JU-1C)과 Client 키(JU-1B)는 뒤 단계라서 그 사이에 쓸 수 없다 (5장 R1).

  3. **`/me` 메뉴 권한은 JU-1B 코드(PermissionService)에 의존한다.** JU-1A에 읽기 경로를 포함해야 한다 (2장).
- PC-A DB 상태를 확인했다 (파일 목록 기준).
  - juprovider: `ju_menu_action`(+detail)은 이미 있고 `ju_client`는 없다.
  - juproject: `tb_*` 3개 + `__EFMigrationsHistory`
- PC-A에서 Claude가 할 수 있는 일
  - 저장소에 파일을 직접 쓸 수 있다 (깊은 경로도 가능, 확인함).
  - 명령은 `.cmd` 더블클릭으로만 실행한다.
  - DB 비밀번호 입력이 필요한 단계는 사용자가 해야 한다.

## 4. `application-dev.yml` 충돌 여부 — 충돌 없음

- juprovider에는 profile 설정이 전혀 없다: `application.yml` 하나, `spring.profiles` 참조 0건, 테스트 코드 0건.
- 수정안
  - 속성 `juprovider.security.jwt.allow-random-secret`(기본 false)을 둔다. `application-dev.yml`에서만 true로 한다.
  - `JwtConfig`는 secret이 없거나 32바이트 미만이고 이 속성이 false이면 기동 실패한다.
- 위험: Tomcat `setenv.bat`에 `SPRING_PROFILES_ACTIVE=dev`가 들어가면 운영에서도 fallback이 켜진다.
  - 대책 1: `ai_dev_env_check.ps1`에 setenv의 `SPRING_PROFILES_ACTIVE` 검사를 추가한다 (값 비교만, 비밀 아님).
  - 대책 2: Jenkinsfile Health Check 뒤에 경고를 추가한다.
- 로컬 실행 예: `java -jar juprovider.war --spring.profiles.active=dev --server.port=18081`

## 5. 401 변경의 영향 — **수정 필요**

현재 코드
- 로그인 실패: `IllegalArgumentException` → 400
- 토큰 없음·만료: Security `JsonSecurityErrorHandler` → 401
- Vue `api.js`: `/auth/login`을 제외한 모든 401에서 세션을 지우고 첫 화면으로 보낸다

| # | 문제 | 제안 |
|---|---|---|
| R2 | 비밀번호 변경에서 현재 비밀번호가 틀린 경우까지 401로 바꾸면 Vue가 즉시 로그아웃시킨다 | 401은 **로그인 실패와 토큰 문제에만** 쓴다. 현재 비밀번호 오류는 400 (사유 메시지 포함) |
| — | 401 응답에서 계정 존재 여부가 드러나지 않아야 한다 | 아이디 없음 / 비밀번호 틀림 / 비활성 사용자 / 비활성 권한을 모두 같은 401 메시지로 응답 |
| — | 구현 | backend에 `AuthenticationFailedException` 추가 → `GlobalExceptionHandler`에서 401로 변환. Security 체인은 이미 401 JSON 응답이라 그대로 둔다 |

**R1 (단계 사이 기능 중단)**
- JU-1A가 `/api/**`에 JWT를 요구하는 순간 문제가 생긴다.
  - Vue 장치 화면은 로그인 화면이 JU-1C에 있어서 쓸 수 없게 된다.
  - Desktop 동기화(`/api/core/sync/**`)는 Client 키가 JU-1B에 있어서 401이 된다.
- 선택지
  - **(가, 권장)** JU-1A·1B·1C를 각각 로컬 commit하고 PC-A 빌드 게이트를 통과시킨다. **push는 JU-1C까지 끝난 뒤 한 번** 하고 Jenkins main을 확인한다. Desktop 동기화만 JU-1A에서 임시로 `permitAll`을 두고 JU-1B에서 닫는다.
  - (나) JU-1A에 "인증 강제" 스위치(기본 off)를 두고, JU-1C에서 on으로 바꾼다. 단계마다 push할 수 있지만, 그동안 운영 코드에 스위치가 남는다.
  - (다) JU-1A~1C를 한 단계로 합친다. 단계가 커진다.

## 6. Client 키 SHA-256 비교 — constant-time 맞음

- `ClientService.verify`
  - 저장된 해시와 입력 키의 SHA-256(hex, 64자)을 `MessageDigest.isEqual`로 비교한다. 길이가 같은 바이트 배열이고 JDK 21에서 constant-time이다.
  - 키는 서버 `SecureRandom` 32바이트, Base64URL이다.
  - 키 원문은 발급·재발급 응답에서만 나가고 로그에 남기지 않는다 (코드에 로그 없음).
  - 재발급하면 `KEY_HASH`를 바로 덮어써서 이전 키는 즉시 무효가 된다.
- 남은 점
  - CLIENT_ID가 존재하는지에 따라 응답 시간이 조금 다를 수 있다 (DB 조회 유무). 키 추측에는 영향이 없어서 그대로 둔다.
  - 인증 실패 횟수 제한이 없다. 이후 과제로 둔다.

## 8. SYS migration Up/Down — Pomelo/MariaDB로 표현 가능

| 단계 | 표현 | 비고 |
|---|---|---|
| 이름 변경 | `RenameTable` → `ALTER TABLE ... RENAME` | MariaDB가 기존 FK(`fk_code_group`) 참조를 같이 갱신한다 |
| 신규 컬럼·테이블 | `AddColumn`, `CreateTable` | |
| ADMIN/USER 생성 | `migrationBuilder.Sql("INSERT INTO sys_auth ...")` | `created_at = UTC_TIMESTAMP(6)` |
| `auth_id` nullable 추가 → 매핑 | `AddColumn(nullable: true)` + `Sql("UPDATE sys_user u JOIN sys_auth a ON a.auth_code = u.role_code SET u.auth_id = a.auth_id")` | |
| 미매칭이면 실패 | `AlterColumn(nullable: false)` | strict mode에서 NULL 행이 있으면 `ALTER`가 오류로 중단된다 (별도 SIGNAL 불필요). sql_mode 확인 필요 |
| FK·인덱스·`role_code` 삭제 | `AddForeignKey`, `CreateIndex`, `DropColumn` | |
| 메뉴 4개, 권한-메뉴 매핑 | `Sql(INSERT ...)` | |
| Down | `role_code` nullable 추가 → `auth_code`로 채움 → NOT NULL → FK·`auth_id` 삭제 → 신규 테이블 삭제 → 이름 원복 | |

**주의**: MariaDB DDL은 트랜잭션으로 묶이지 않는다. 중간에 실패하면 DB가 반쯤 바뀐 상태로 남으므로 **백업이 필수**다.

생성 절차 (PC-A)
1. 탐색기에서 `.cmd` 더블클릭 → `dotnet ef migrations add SysCoreSchema`. PC-A user-secrets가 SET이라 가능하다.
2. 생성된 Up/Down을 Claude가 위 순서로 직접 고친다.
3. `dotnet ef migrations has-pending-model-changes`로 스냅샷 일치를 확인한다.

## 11. 추가 사용자 승인 항목
