# C5 설계 검토안 — 수집 설정 DB 이전 · 역할·규칙 검사 (설계만, DB·코드 변경 없음)

## 1. 목표
C4에서 Desktop 내장(GTEC)으로 둔 것을 서버 정의로 옮기고, 저장 시 검사한다. 이후 Desktop 내장 설정은 "서버 값 없을 때만" 쓰는 대체값으로 축소.

## 2. 스키마 (migration, 별도 승인)
| 대상 | 추가 | 비고 |
|---|---|---|
| `ju_protocol_group` | `FRAME_RULE` longtext NULL, `CMD_GAP_MS` int NOT NULL DEFAULT 0, `INIT_ROUTINE` varchar(500) NULL, `INIT_DELAY_MS` int NOT NULL DEFAULT 500 | FRAME_RULE = Frame Rule JSON v1(`start` 포함), INIT_ROUTINE = PTL_CD 쉼표 목록(순서 유지) |
| `ju_protocol` | `PTL_ROLES` varchar(50) NULL, `PTL_ACTION` varchar(8) NULL, `EXPECT_RULE` varchar(500) NULL, `IDEMPOTENT_YN` varchar(8) NULL | ROLES = PROL 코드 목록, ACTION = PACT 코드, EXPECT = `{"startsWith"}`/`{"regex"}` JSON |
| 공통코드 | `PROL`(INFO/CONTROL/DATA), `PACT`(NONE/START/PAUSE/STOP) | |
| 신규 `ju_data_channel_map` | `MAP_ID` PK, `DEV_CD`, `CHANNEL_KEY`, `PTL_CD` NULL, `DAT_GR_CD`,`DAT_CD`,`DAT_IDX`, `SCALE`, `OFFSET_VAL`, `USE_YN`, `SORT_ORD`; UK(DEV_CD, CHANNEL_KEY, PTL_CD, DAT_GR_CD, DAT_CD, DAT_IDX) | FK: 장치·데이터 태그. 없으면 `TAG_ID=CH<n>` 임시 변환 유지 |
- 해석 규칙은 기존 `ju_protocol_packet.PARSE_RULE`(RX 패킷) 재사용 — 컬럼 추가 없음, JSON 검사만.
- `PTL_TYPE` 의미 확정: PROT0000 POLL · 0001 TX_ONLY · 0002 RX_STREAM · 0003 TX_RX.

## 3. 데이터 정정 (같은 migration, GTEC 실장비 검증값)
- GTEC 그룹: FRAME_RULE `{"v":1,"kind":"DELIM","start":"{","end":"[CR][LF]"}`, CMD_GAP_MS 200, INIT_ROUTINE `GTEC0301,GTEC0001,GTEC0002,GTEC0100`, INIT_DELAY_MS 500
- 검증된 7개만 정정: 0000·0001·0002 TX_RX/INFO(+EXPECT), 0100 TX_ONLY/CONTROL(멱등), 0300 TX_ONLY/CONTROL/START, 0301 TX_ONLY/CONTROL/STOP, 0400 RX_STREAM/DATA + RX 패킷 PARSE_RULE TEXT JSON. 나머지(0101~0105·0200·0201·0003·0401·0402)는 그대로 두고 목록 보고
- `ju_data_channel_map`: SDEV_GTEC01 CH "1"~"4" → DG_GTEC01/GTEC-DATA-01~04
- 되돌리기: 변경 전 값을 백업 테이블에 저장 → down 스크립트로 복원 + 컬럼·테이블 제거

## 4. 검사 (Protocol CRUD 저장 시, 서버)
| 규칙 | 오류 |
|---|---|
| PTL_ROLES 1개 이상, PROL 코드만 | 400 |
| RX_STREAM → DATA 역할 + RX 패킷 PARSE_RULE(JSON v1) 필수 | 400 |
| TX_ONLY·TX_RX·POLL → 송신 표현식(TX 패킷 또는 PTL_VAL) 필수, 표현식 문법(`[..]` 이름·16진) | 400 |
| PARSE_RULE·FRAME_RULE JSON: v=1, kind 허용값, trim 2글자 등 (Desktop RuleReader와 같은 규칙) | 400 |
| EXPECT_RULE: 키 1개, regex 컴파일 가능 | 400 |
| INIT_ROUTINE: 같은 그룹의 사용 중 PTL_CD, RX_STREAM 불가 | 400 |
| STOP 액션 PTL 은 멱등 아님(재시도 안 함) | 자동 |
- 규칙 문법을 서버(Java)·Desktop(C#) 두 곳에 두게 됨 → 공통 테스트 벡터(JSON 파일)로 양쪽 테스트.

## 5. 계약·API
- 내려받기 응답(C4): 그룹에 `frameRule, cmdGapMs, initRoutine[], initDelayMs`, 프로토콜에 `roles[], action, expect, idempotent` 추가(필드 추가만, 기존 필드 유지 → revision 값은 바뀜). 신규 `GET /api/core/sync/data-map?devCd=`.
- Protocol Action 계약 → **v2** (C0-Q8: clearable 포함). v1 호출 유지.
- Desktop `CollectionPlanBuilder` 우선순위: 서버 값 → (없을 때만) 내장 설정 → 기본값. 경고에 출처 표시.

## 6. 기준 브랜치 (중요)
Protocol CRUD·Action 계약(PR-1~3, migration 06)은 `feature/integration-1`(main 미병합)에 있고, 수집 경로(C1~C4b)는 main 기반 `feature/collect-c4`. C5는 둘 다 필요 → `feature/collect-c5` = integration-1 + collect-c4 **로컬 병합**(main 아님)으로 시작 제안. migration 번호도 06(통합 대기)·07(SYSINFO-02 `ju_schema_version` 예정) 뒤 **08** 제안.
