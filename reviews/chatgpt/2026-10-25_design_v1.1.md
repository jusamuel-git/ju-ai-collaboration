앞서 전달하려던 ChatGPT 통합 구조 설계 v1에 중요한 전제 수정이 있습니다.

이 수정본(v1.1)을 기준으로 역검토해 주세요.

아직 구현/DB 수정/migration/파일 삭제는 하지 않습니다.

[최상위 아키텍처 원칙]

JuProject와 JuProvider는 동일한 시스템 DB를 공유하는 구조가 아닙니다.

방향은 항상:

SYS (JuProject)
→
JU (JuProvider)

입니다.

그러나 가장 중요한 전제는:

JuProvider는 JuProject가 전혀 없어도 독립적으로 완전히 동작해야 합니다.

실제 설치 환경에서 JuProject 또는 SYS 데이터를 사용할 수 없는 경우가 있기 때문입니다.

따라서:

JuProject DB와 JuProvider DB를 공유하지 않음

SYS 테이블을 JU에서 FK로 직접 참조하지 않음

JU 실행에 SYS 접속을 필수 조건으로 만들지 않음

SYS → JU 연동은 선택적 외부 연동으로 설계

SYS가 없으면 JU 자체 데이터만으로 모든 Core/Device/Experiment 기능이 동작해야 함

[SYS와 JU의 User는 다른 개념]

sys_user와 ju_user를 같은 엔티티로 통합하지 않습니다.

sys_user

JuProject/SYS의 사용자

고객/사업/운영 시스템의 계정 관리

Site/Dept 등 상위 조직정보와 연결

향후 고객이 사용하는 시스템과 서비스 관리가 주 목적

ju_user

JuProvider 자체 Core 사용자

JuProvider 로그인/운영

ju_auth

ju_menu

ju_menu_action

Protocol/Device/Data/Experiment 접근

SYS가 없어도 존재하고 사용할 수 있어야 함

따라서 기존 ju_user를 sys_user로 대체하지 않습니다.

[SYS 영역 후보]

JuProject에서는 다음 System 구조를 검토합니다.

sys_site

sys_dept

sys_user

sys_auth

sys_menu

sys_auth_menu

sys_auth_action

sys_code_group

sys_code

필요 시 sys_language / sys_multi_lang

향후 고객/서비스 관리 테이블

기존 JuProject의 tb_user, tb_code_group, tb_code를 이 방향으로 발전시키는 것이 적합한지 검토해 주세요.

[JU Core 영역]

JuProvider는 기존 ju_ Core 구조를 기본적으로 유지하는 방향으로 다시 검토합니다.

ju_user / ju_user_detail

ju_auth / ju_auth_detail

ju_menu / ju_menu_detail

ju_menu_action / ju_menu_action_detail

ju_com_group / ju_com_code

ju_language / ju_multi_lang

ju_sys

기타 Core 테이블

기존 JuProvider의 자연키, YENO, detail, 다국어 구조를 SYS 규칙에 맞추기 위해 무조건 변경하지 않습니다.

각각 실제 장단점과 변경 비용을 다시 평가해 주세요.

[Site / Dept]

Site와 Dept는 SYS에는 필요한 핵심 후보입니다.

하지만 JuProvider에 ju_site, ju_dept를 반드시 추가한다는 전제는 취소합니다.

현재 JuProvider Core/Device/Experiment 자체 기능에서 Site/Dept가 실제로 필요한지 조사해 주세요.

필요하다면 SYS의 Site/Dept와 같은 테이블을 공유하는 것이 아니라 JU 자체 모델을 별도로 가져야 합니다.

[DB 규칙]

SYS와 JU의 DB 규칙을 반드시 동일하게 만들지 않습니다.

공통으로 가져갈 수 있는 것은 다음과 같은 설계 원칙입니다.

다국어 가능성

PK 전략

코드 체계

실제 테이블 구조

따라서 기존 JuProvider 37개 테이블을 JuProject 규칙에 맞추기 위해 대규모 재설계하지 않습니다.

[JU 인증/권한]

JuProvider 자체 인증은 반드시 완성해야 합니다.

목표:

JU Login
→ JWT 또는 적합한 인증 방식
→ /me
→ ju_user
→ ju_auth
→ ju_menu
→ ju_menu_action
→ API/Action Permission

SYS 인증에 의존하지 않습니다.

JuProject의 JWT 구현 개념은 참고할 수 있지만 JuProvider 자체 Spring Security로 독립 구현합니다.

기존 AUTH_ATTR JSON을 계속 사용할지,
ju_auth_menu / ju_auth_action 같은 관계 구조가 더 적합한지는 JU 내부 설계 문제로 다시 검토해 주세요.

[JU 업무 도메인]

다음은 JuProvider 독립 도메인입니다.

Protocol Group
→ Protocol
→ Protocol Packet
→ Device
→ Data Group
→ Data Tag
→ Experiment
→ Run
→ Collection
→ Viewer

SYS가 없어도 전체 흐름이 동작해야 합니다.

[SYS → JU 연동]

이번 구현 범위가 아니라 향후 구조입니다.

향후 필요하면:

SYS
→ API / Sync
→ JU

방향으로 필요한 정보만 전달합니다.

검토할 사항:

어떤 SYS 정보가 JU에 실제 필요한가

JU 내부에 복제/캐시해야 하는가

외부 ID 매핑이 필요한가

SYS 연결이 끊겨도 JU가 계속 동작할 수 있는가

현재 단계에서는 구현하지 않습니다.

JU는 SYS보다 독립적이며 SYS 완료를 기다리지 않고 개발 가능해야 합니다.

[역검토 요청]

현재 실제 코드/DB를 기준으로 다음을 검토해 주세요.

이 SYS → JU 단방향/선택적 연동 원칙이 현재 구조와 충돌하는 부분

ju_user와 sys_user를 완전히 독립적으로 유지할 때 문제 여부

기존 ju_user/auth/menu/action 구조에서 그대로 살릴 부분

JU 인증/권한을 완성하기 위해 실제로 변경해야 할 부분

JuProvider에 Site/Dept가 실제 필요한지

기존 JuProvider의 자연키/YENO/detail/다국어를 유지하는 경우의 장단점

SYS만 bigint PK + Y/N + snake_case 등의 새 규칙을 적용해도 문제가 없는지

JuProject의 기존 tb_user/code를 sys_*로 변경하는 비용

SYS→JU 연동 시 향후 필요한 최소 식별키/매핑 구조

JU가 완전히 Offline/Standalone으로 실행되기 위해 필요한 데이터와 기능

기존 37개 JuProvider 테이블 중 현재 구조 그대로 유지할 것 / 수정할 것 / 보류할 것

Protocol→Device→Data→Experiment 흐름에서 Core 인증/권한과 연결되어야 할 지점
