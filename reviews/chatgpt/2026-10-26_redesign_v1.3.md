- 작성: ChatGPT
- 기준일: 2026-10-26
- 목적: 2026-10-25의 JU-0/JU-1/SYS 미커밋 구현을 현재 확정된 PC-A 환경에서 작은 단계별로 재검증·반영
- 원칙: 기존 구현은 폐기하지 않고 재사용 후보로 두며, 단계별 Build Gate를 통과한 뒤 별도 commit한다.

## 1. 최상위 기준

SYS(JuProject) → JU(JuProvider)는 선택적 단방향 연동이며 JU는 SYS 없이 독립 실행한다. DB 공유/직접 조회/SYS PK의 JU FK 사용은 하지 않는다.

현재 결정으로 v1.2를 수정한다.

- JU Site 계층은 유지한다. Level 1은 부서 상위, 하위 Level은 장치 위치이며 SYS Site/Dept 복제가 아닌 JU 자체 모델이다. 실제 schema/API는 JU-3 Device 직전에 설계한다.
- JU 권한 Source of Truth는 `ju_auth.AUTH_ATTR` JSON + MACT 비트다. `ju_auth_menu/ju_auth_action` 관계 테이블 전환 권고는 폐기한다.
- SYS-0과 SYS-1은 하나의 SYS-01 단계로 진행한다.
- Desktop Client 인증과 User 인증은 분리한다.
- 초기 JU admin은 seed 기본 credential + 첫 로그인 비밀번호 변경 강제를 유지한다.

모든 단계는 `Claude 적합성 확인 → 해당 단계만 적용 → PC-A 로컬 빌드/테스트 → ChatGPT 검토 → 사용자 승인 → commit/push → Jenkins main` 순서다. DB migration 적용은 Build와 별도 승인한다.

2. 신규 컬럼/테이블 생성

- `created_by/updated_by` BIGINT, FK 없음: 승인 권장
- `sys_auth_menu` surrogate PK + `(auth_id,menu_id)` UNIQUE: 승인 권장

검증:

Commit 후보: `feat(sys): introduce core sys schema with data-preserving migration`

### JU-1A — 서버 User Authentication / JWT

범위:
- JWT config/dependency
- login, `/me`, password change
- 사용자 JWT Security chain
- login success/fail 기록
- password-change-required

A:
- default/production: `JU_JWT_SECRET` 없거나 기준 미달이면 기동 실패
- dev profile만 임시 random secret + WARNING
- `application-dev.yml` 권장
- Jenkins/Tomcat은 dev profile 금지

B:
Login 응답 새 계약 승인 권장:
`accessToken`, `expiresAt`, `user{userId,loginId,userName,authId,authType,passwordChangeRequired}`.
`authAttr`은 login에서 제거하고 `/me`가 현재 권한/메뉴를 담당한다.

D:
AuthService는 이번 JU-1에서는 Backend JPA 유지. Core 이전은 별도 리팩터링으로 보류한다.

F:
잘못된 ID/password는 동일한 401. Validation 오류만 400.

Commit 후보: `feat(auth): add juprovider JWT user authentication`

### JU-1B — Menu Action Permission + Desktop Client Authentication

범위:
- AUTH_ATTR parser/PermissionService
- DynamicAction 권한 검사
- `ju_client`, detail
- Client DAO/Service/Filter
- Admin Client API
- `/api/core/sync/**` Client 인증
- Desktop Client key header/config
- migration 05

C:
- 직접 조회 API = JWT + PW_OK
- 변경/실행 Dynamic Action = Menu Action 권한
- sync/upload/audit/error = Client 인증
- 모든 `/api/core/*`를 지금 억지로 Action화하지 않는다.

E:
서버 CSPRNG 32-byte 이상 Client Key → SHA-256 hash 저장 승인 권장.
원문은 발급/재발급 때 1회만 반환하고 로그 금지, 재발급 즉시 이전 key 무효, 비교는 constant-time 권장.

AUTH_ATTR:
- 관계형 권한 테이블 추가 안 함
- 9자리 legacy 지원
- 11자리 = menu code + permission byte
- admin FF, 비-admin 초기 01
- 권한은 DB에서 읽어 즉시 반영

Commit 후보: `feat(auth): add action permissions and client authentication`

### JU-1c Desktop — User Login / Offline Authentication

기존 Phase 명칭을 유지한다.

- 최초 사용자 offline 로그인 불가

- 구현 전 LOCAL_USER/OFFLINE_TOKEN의 만료·보호 방식을 다시 조사
- 평문 서버 password 로컬 저장 금지

## 11. 결론

PC-A의 main baseline은 환경검사 FAIL 0, 5개 로컬 build PASS이므로 재설계 기준점으로 사용한다.

10/25 미커밋 구현은 폐기하지 않되 한 번에 반영하지 않는다. 환경 → 설치 DB → Runtime 정합성 → SYS → JU User 인증 → JU 권한/Client → Vue → Desktop offline 순으로 분해한다.

각 단계에서 문제가 생기면 원인을 한 commit과 한 Build Gate 안에서 찾을 수 있어야 한다.
